# Supported analysis and interpretation

| Area              | Supported evidence                                                                                                                                                                 | Limits and interpretation                                                                                                                                                                                                                              |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Docker            | Dockerfile `FROM` stages, stage aliases, `COPY --from` links, `ARG`/`ENV` names, final-stage user signal                                                                           | Does not build images or resolve base image users; missing or explicit root users produce review signals; inherited image users are not resolved. Dynamic or malformed instructions are diagnostic.                                                    |
| Compose           | YAML service, named network/volume resources, `depends_on`, named mounts and network links                                                                                         | YAML core data only; includes, extends, expressions and external resources are not executed/resolved. Evidence can cover the configuration rather than an exact property token.                                                                        |
| GitHub Actions    | Workflow jobs, static `needs`, environment names and action references                                                                                                             | Reusable/dynamic workflows and expressions are not expanded. No workflow execution or permission proof. Broad permissions, pull-request-target and unpinned actions are review signals.                                                                |
| Environment       | Names from environment files, Docker/config declarations and source references                                                                                                     | No environment values or credentials appear in the environment inventory.                                                                                                                                                                              |
| Jest/Vitest       | Conventional `.test`/`.spec`/`__tests__` files; imported aliases, supported globals, modes and parameterized declarations                                                          | Only supported literal declarations and resolved static call/reference sites link to source symbols. Test existence and a call edge do not prove test execution or assertion quality. Mixed/unknown frameworks remain uncertain.                       |
| Coverage          | LCOV line counts and Istanbul `coverage-final.json` statement counts                                                                                                               | Metrics stay separate. Repeated LCOV records merge. Only known archive source paths or unique normalized suffix matches are accepted. Missing/invalid records are diagnostic. Reports may be stale or fabricated; no fresh execution is implied.       |
| Dependencies      | npm package manifests as declared ranges; npm package-lock v2/v3 packages and pnpm package keys as exact resolved versions                                                         | npm ecosystem only. Unresolved/non-semver lock entries are diagnostic. A declared range is never treated as an installed version. Other package managers/ecosystems are unsupported.                                                                   |
| Built-in security | Supported GitHub/Neon/cloud credential tokens, private-key headers, credential URLs, literal credential-like assignments, dynamic evaluation/shell calls and configuration signals | Fixed descriptions and source location only; detected values are redacted. No general taint analysis, runtime verification, exploitability proof or complete credential discovery. Literal safe command strings are negative fixtures.                 |
| Semgrep           | Bundled local dynamic-eval, dynamic-shell and TLS-disable rules; known source positions                                                                                            | Requires a trusted installed executable. No auto/registry config, project config or source snippets are persisted. Unknown rule IDs and outside-file locations are rejected.                                                                           |
| OSV               | Optional trusted OSV-Scanner source/lockfile command or fixed OSV querybatch fallback, bound to resolved npm versions                                                              | Opt-in and deployment policy required. API fallback queries up to 100 unique versions; CLI accepts up to 20 supported locks. Pagination/limits cause partial results. Unsupported severity is `unknown`; absence of findings is not proof of security. |

All three scanner statuses are displayed independently: completed, partial, disabled, unavailable or failed. Built-in extraction uses deterministic rule version `rules-v1`. External checks record their tool adapter/version and timestamp; advisories can change over time, so external snapshots are not reproducible across different lookup times.

References for operator compatibility: [Semgrep CLI](https://docs.semgrep.dev/cli-reference), [OSV-Scanner source scanning](https://google.github.io/osv-scanner/usage/scan-source), [OSV API](https://google.github.io/osv.dev/api/) and [YAML parser](https://eemeli.org/yaml/). Changes to scanner versions or output formats require rerunning the adapter fixtures before deployment.

When supported credential signals occur anywhere in the snapshot, external vulnerability lookup uses the sanitized metadata-only OSV API path, even when an OSV CLI is configured. Raw lockfiles from those snapshots are not passed to external scanner commands; redacted identifiers are omitted and scanner status/messages disclose packages that were not queried.
